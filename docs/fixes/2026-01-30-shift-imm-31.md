# Fix: Shift count 31 emits reserved immediate encoding

**Date**: 2026-01-30  
**Author**: AI Agent  
**Severity**: High  
**Component**: Instruction Selection / TableGen

## Problem

### Symptoms
- `test_64bit` failed on `one << 63` with the high 32 bits returning `0x00000002`
- Minimal repro returned the wrong high word:
  ```c
  uint64_t v = 1ULL << 63;
  return (int)(v >> 32); // expected 0x80000000
  ```
- Assembly showed `SHL ... #$1f` for a shift-by-31, but the result behaved like a shift-by-1.

### Root Cause
The barrel-shifter encoding reserves shift count `0x1F` to mean "shift by A".
The backend was emitting the immediate form for constant `31`, which the
hardware interprets as variable-by-A instead of a constant shift. This produced
wrong results for any shift amount that required a 31-bit step (e.g., `1ULL << 63`).

## Investigation

### How the Issue Was Isolated
1. Created a minimal test for `(1ULL << 63)` and returned the high 32 bits.
2. Observed wrong result (`0x00000002`) even though the shift amount was constant.
3. Inspected the emitted assembly and saw `SHL R0,R0,#$1f`.
4. Cross-checked ISA encoding: count `0x1F` is reserved for variable shifts.

### Debug Output
```
SHL R0,R0,#$1f   ; assembled as "shift by A" (reserved count)
```

## Solution

### Changes Made
Files modified:
- `llvm/lib/Target/M65832/M65832InstrInfo.td`

Added an immediate operand that excludes `31`, and used it for all constant
barrel-shifter forms so the selector emits the variable-by-A form when the
count is 31.

```diff
+def imm5_non31 : Operand<i32>,
+                 ImmLeaf<i32, [{ return isUInt<5>(Imm) && Imm != 31; }]> { ... }

-def SHLR : ... (ins GPR:$src, i32imm:$cnt) ...
+def SHLR : ... (ins GPR:$src, imm5_non31:$cnt) ...
```

### Why This Fix Works
The immediate encoding cannot represent a constant 31 without colliding with
the "shift by A" mode. By excluding `31` from immediate selection, the
instruction selector materializes the count in `A` and emits `SHL ... ,A`,
which correctly handles a count of 31.
